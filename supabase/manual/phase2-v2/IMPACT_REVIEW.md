# Compatibility / impact review

| Flow | v1 concern | v2 behavior and staging gate |
|---|---|---|
| Active customer/admin login | Blanket policies could hide profile reads on failures | Active actor helper remains true; existing authorized profile reads continue. Install cleanup companion first so inactive/NULL/query-error sessions are removed. Verify both audiences independently. |
| Registration and Google signup | New constraints could block server profile initialization | Existing signup trigger still owns role assignment and sets is_active=true. Global write invariant requires a pre-existing active Super Admin and adds a serialization point. Test email-confirmation-required and immediate-session branches, Google first login and normal sign-in. No changes to callback URLs/settings now. |
| Password recovery | Customer initialize() can throw on a protected profile read | Auth endpoints do not use the Data API hook, but frontend initialization currently does. Companion recovery handling must validate the recovery event/user independently; it must never let a profile failure bypass PASSWORD_RECOVERY proof. Test expired/reused links and inactive/NULL accounts under the explicit product policy. No auth-setting changes. |
| Public catalogue | Blanket SELECT restrictions would deny public data to signed-in inactive accounts | Public SELECT operations are excluded from the private policy manifest. Public read RPCs must be explicitly fingerprinted/reviewed. Canonical RLS-table requests can use original public policies. Custom schemas/views/noncanonical routes require explicit review; no broad exception is assumed. |
| Checkout | Public anonymous and signed-in private paths must stay distinct | Anonymous guest checkout keeps its grants and behavior. Signed-in inactive checkout is DENIED, not silently downgraded to guest with a stale JWT. After successful local logout, guest checkout can proceed using the anonymous path. Test all checkout overloads, discounts/free gifts/loyalty and idempotency. |
| Orders/dashboard/products | Existing RLS checks must survive | Existing policies are unchanged; private reads/mutations add actor-active checks per manifest. Public product SELECT stays public; admin mutations are gated. RPCs remain protected by default for inactive callers. Verify ALL dashboard data/charts/export unchanged for active admins. |
| Storage | Hook alone gives no protection | Use independently reviewed storage.objects policies. Normally protect private SELECT and authenticated mutations. Public file downloads remain public by design. The public flag does not grant uploads/deletes. Confirm service-role internal jobs and upload/delete/avatar paths. |
| Realtime | Data API pre-request hook is irrelevant | Validate protected Postgres Changes delivery against underlying row policies with the same JWT after deactivation. Public catalogue/video events retain intended public semantics. Private Broadcast/Presence, if deployed, need separate authorization gates. DELETE-event behavior and already delivered/in-flight events require explicit tests; don't promise revocation of past data. |
| Super Admin management | v1 permitted direct self-PATCH and could remove the last admin | Browser assignments now require the dedicated RPC; self changes are allowed through RPC only when the final invariant still holds. Role-catalogue browser editing is disabled. Trusted maintenance remains possible but cannot delete/demote/deactivate the last active Super Admin with triggers installed. |
| Existing NULL profiles | Treating NULL as true would grant access unexpectedly | NULL stays denied. Aggregate counts are reported without modifying rows. Approve legitimate legacy activations individually; zero active Super Admins blocks installation pending separately authorized recovery. |

Public read availability does not mean an inactive account may access previously protected fields through a public view or broad permissive policy. The live coverage audit must verify field exposure and view security-invoker settings separately.
