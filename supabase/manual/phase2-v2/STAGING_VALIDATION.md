No SQL, API probe or production request was executed during this proposal review. This runbook requires separate approval and an isolated staging project with disposable accounts/rows. Never copy production session tokens into logs or proposal files.

1. Export 00 from the actual target staging project and record PostgreSQL/PostgREST versions. Compare profile columns, nullable flags, old guard definition/ACL/owner, trigger ordering, all grants, role memberships, public/privileged RPC overloads, exposed/default schemas, views, Storage policies and active/NULL account counts. Confirm the target has an active Super Admin. Lack of required permissions or mismatched schema is a STOP, not permission to change security ad hoc.
2. Populate policy-manifest.template.json; map every client table/RPC/Storage/Realtime operation to public-read or protected-operation status. Review hashes from the same environment; staging OIDs/fingerprints cannot be reused blindly for production. Confirm no existing hook/pre-config/environment override needs composition.
3. Apply approved Angular companion changes to the staging build, then approved migration 10. Test normal profile editing, direct PATCH denial for ALL authenticated roles including Super Admin, role-catalogue browser denial and the dedicated role's NOLOGIN/NOBYPASSRLS/no-browser-membership properties. Attempting to set an arbitrary application GUC must not unlock privileged writes.
4. Last-Super-Admin tests: with one active Super Admin, reject self-demotion/deactivation, profile deletion, Auth-user cascade deletion, role-catalogue rename/delete and TRUNCATE. With two, allow one authorized removal, then reject the last. Launch two concurrent RPC calls that would remove both; at most one can commit. Repeat at READ COMMITTED and REPEATABLE READ/SERIALIZABLE using an isolated harness; retry serialization failures only where safe. Trusted service-role writes must obey the same surviving-admin invariant. Verify no partial business-row changes remain after rejection.
5. NULL tests: read counts without updates; no NULL account gains protected access or counts as active Super Admin. Explicit authorized activation of a reviewed NULL target works. Zero true Super Admins blocks migration; no automatic bootstrap or backfill.
6. Install migration 20 using reviewed manifests/hashes, then STAGING-ONLY probe 30. Through the real staging Supabase REST endpoint, POST /rest/v1/rpc/phase2_request_context_probe with an active Super Admin JWT. Assert hook_marker=v2, expected request path and POST method. Repeat fresh independent requests and after connection-pool reuse/reload; a cached previous result is not proof. Probe output intentionally excludes tokens/claims/headers/PII.
7. Verify active REST/RPC requests work; deactivate a disposable account while retaining its original JWT. Private table reads/writes and protected RPC side effects must be denied immediately on subsequent requests. Explicitly allowed public read RPCs still work only when the reviewed overload fingerprint matches. Test unknown/new/changed overloads, encoded paths, Accept-Profile/Content-Profile changes, views and a missing/incorrect hook. A plain 403 from another policy is insufficient evidence the hook ran. Missing marker or provider-ignored config blocks release; do not claim actual Supabase verification until this passes.
