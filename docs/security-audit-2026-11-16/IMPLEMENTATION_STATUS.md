## Compatibility boundaries

- **Search by Image:** inspected `customer-image-search.component.ts`, `customer-image-search.service.ts`, `product-image-embedding.service.ts`, `dino-image-embedding.service.ts` and its worker. File selection feeds browser embedding generation; public search/index-count RPCs are `search_products_by_image` and `get_customer_image_search_index_count`. No Storage call was found in that inspected search chain. This does not establish deployed/external behavior. Preserve both Guest and Customer search grants, current file handling, model/worker behavior, ranking and index maintenance. Any deployed search upload dependency discovered in metadata/traffic must remain authorized with its current ownership semantics. Do not infer that catalog buckets are exclusively Admin from their names.
- **Avatars:** `src/app/shared/utils/avatar-upload.util.ts` and `src/app/core/services/auth/admin-auth.service.ts` upload to `avatars`, under the current Auth UUID folder. Preserve Customer/Admin uploads, image processing, public URL behavior and profile linking. Test foreign-folder writes/deletes and path/bucket moves. Do not apply a blanket Admin-only rule to `storage.objects` or `avatars`.
- **Catalog/media:** active Admins must manage assets uploaded by other Admins; an owner-only media rule would break shared catalog administration. `media_assets.bucket_name` can direct deletion to a stored bucket; reconcile allowed buckets and existing callers before narrowing paths. Database-row and object policies must be deployed/tested together. Media soft deletion does not revoke an intentionally public URL.
- **Public reads:** preserve bucket flags and intentional product image/video downloads, including anonymous reads and existing cached URLs. Restrict mutation commands, rather than a blanket restrictive `FOR ALL` policy. A new permissive Admin policy alone will not neutralize broader permissive writes.
- **Sessions and performance:** no client configuration, route guard, token storage, auth persistence, worker, image processing, UI, index or infrastructure change is included. Trusted database lookup design must be reviewed with existing indexes and realistic staging plans before release.

1. Obtain the consolidated deployed export in the ignored inbox described in `METADATA_REQUEST.md`, plus deployed Edge source/configuration and actual hosted exposed-schema settings. Review completeness, exact definitions and every overlapping permissive/restrictive policy.
2. Reconcile actual enum/role names, activation semantics, columns, ownership relations, grantors/memberships, function overloads, bucket use and trusted owners. Compare effective privileges, not only explicit ACL rows. Record fingerprints for release preconditions.
3. Produce a release migration outside the current manual proposal set. Preserve untouched policies and object identities. Add narrowly scoped restrictions; replace/revoke only reviewed existing paths. Make reruns recognize the exact installed state and fail on unexpected drift, rather than silently overwriting unknown policies/functions. Current drafts are **not a completed idempotent release**.
4. Generate the paired rollback from that same before-state: exact policy definitions/roles/commands, changed function bodies/attributes/owners/EXECUTE ACLs and original table/column/schema grants with grant options/grantors where applicable. Remove only newly introduced objects in dependency order, without CASCADE or blanket GRANT ALL. `11_core_controls.rollback.sql` is an explicitly incomplete, rollback-ending skeleton; it is **not** the exact requested rollback yet. Restoring old permissions can reopen the original vulnerabilities and requires its own reviewed decision.
5. Rehearse migration twice on an explicitly selected staging clone; verify second-run behavior and reject drift. Run the SQL/API/Storage/RPC matrix, including inactive Admin, active Super Admin, checkout concurrency/replay and rollback/roll-forward. A SQL transaction cannot roll back Storage API uploads or external side effects; use operator-approved staging assets and verify cleanup separately.
6. Capture results, unresolved gaps and the exact forward/rollback artifacts for review. Obtain separate explicit production approval before any execution. During a later approved release, recheck metadata drift, apply the reviewed transaction, run read-only postchecks and approved smoke checks, and stop on any unexpected authorization or compatibility result.
