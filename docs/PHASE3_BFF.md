# Phase 3 — server-managed authentication (implemented, production activation disabled)

## What changed

The previous Angular SDK performed password login directly against Supabase. Supabase correctly returned an access/refresh token pair to its caller, which was the browser. Phase 2 local cleanup could not change that architecture.

In the opt-in BFF build, browser login, registration, Google authorization, recovery, password updates and logout call same-origin `/api/{customer|admin}/auth/*`. Node exchanges credentials/codes with Supabase, validates the user and current active audience profile, encrypts credentials in Redis and sets an opaque 256-bit session cookie. Responses contain only a deliberately small user DTO, a token-free `{user}` session view and profile data. No Supabase token cookie is sent to the browser.

The existing query, RPC and Storage builders are retained. In BFF mode their fetch transport targets `/api/{audience}/supabase/{rest|storage}/v1/*`, strips browser Authorization/apikey headers and uses same-origin cookies. Node uses that audience's server-held user JWT for upstream requests, preserving existing RLS. Unknown routes, schemas, RPCs, profile privilege fields and cross-customer avatar paths fail closed. Private/customer resources require a current active profile on each request. Public catalogue/search/media and guest checkout retain explicit anonymous paths. Expired signed-in checkout is rejected rather than silently converted to guest checkout. No mutation is automatically retried.

Stability repair: CSRF validation failures may refresh the nonce and resend once because the BFF rejected the request before its handler ran. Network errors and 5xx never replay a mutation. CSRF acquisition shares in-flight requests and briefly shares failures to avoid outage storms. Session validation still checks live authorization on subsequent reads. Redis reconnects automatically after temporary disconnects and has no offline command queue or memory fallback. See [the investigation](BFF_STABILITY_INVESTIGATION.md) and [startup instructions](LOCAL_STARTUP.md).

Realtime uses a same-origin EventSource relay. Node authenticates the upstream WebSocket and enforces allowed tables and private owner filters. It checks sessions before relaying private events and during heartbeats, updates upstream authorization after refresh and closes on expiry/logout. JWTs never appear in browser socket frames, EventSource URLs or SSE payloads. This implementation covers the actual Postgres Changes consumers in the repository; it does not invent a general Broadcast/Presence API.

## Security controls

- Separate `__Host-nestora-admin` and `__Host-nestora-customer` cookies: Secure, HttpOnly, SameSite=Lax, Path=/, no Domain. New Admin sessions ignore remember-me and enforce 7 days absolute and 12 hours idle, with a cookie Max-Age no longer than 7 days. Existing Admin cookies and absolute deadlines retain their original bounds. Customer sessions retain 8 hours/1 hour for session-only and 30 days/7 days for remembered; only remembered Customer cookies have persistent Max-Age. Recovery sessions are limited to password changes and expire after 10 minutes. Active requests renew server-side credentials within 60 seconds of access-token expiry without extending the absolute session deadline.
- Shared Redis is mandatory in the production entry point; no runtime memory-store fallback exists. Records use AES-256-GCM, with the Redis record key as authenticated context. Opaque cookie IDs are hashed for Redis keys. Redis TLS is required in production. Use a dedicated primary Redis endpoint, TLS authentication, a private network, persistence/HA appropriate to your hosting and a no-eviction/capacity policy. The implementation uses the normal Redis client, not a Redis Cluster discovery client.
- Refresh is serialized across instances by renewable Redis leases. Credential writes are fenced by the owning lease. Rotated refresh credentials are committed before later upstream profile calls. Logout atomically deletes the session and saves an encrypted revocation job under that lease, then releases the session lock before calling Supabase. A delayed refresh cannot recreate the session. Cookie clearing is audience-specific. Upstream revocation uncertainty is reported separately; already-issued JWT expiry is still governed by Supabase.
- Mutations require an exact configured Origin and a CSRF header matching a Secure HttpOnly browser nonce cookie. Cross-site requests fail. Tokens used for CSRF are not authentication credentials. Shared Redis rate limits cover request volume, IP/account login attempts and Realtime subscription creation. Browser-supplied JWTs are not accepted.
- Google uses server-side PKCE, an encrypted one-time flow record and a browser-bound HttpOnly flow cookie. Signup/recovery email redirects include an opaque flow lookup ID so email links can work across browsers without transferring a JWT. Cross-browser signup verifies the email but then requires an explicit login, avoiding silent login CSRF. Recovery links grant only password-reset capability. Codes/verifiers and provider tokens are never returned in Angular session responses.
- API responses are private/no-store. The Angular service worker excludes `/api` navigation, and browser requests bypass it explicitly. Credential-bearing JSON/text and JWT-shaped values are blocked at egress; current session credentials are also checked in proxied byte responses. Error responses do not reflect upstream credentials or request bodies. Application logging is disabled; the proxy example avoids logging callback query strings.
- The Nginx example includes CSP and other browser headers. Its `connect-src` intentionally excludes Supabase: the BFF build uses `/api` for authenticated traffic. Public media URLs remain anonymous. Review model/CDN endpoints used by visual search in staging. HttpOnly prevents reading session cookies from JavaScript; it does not make arbitrary XSS-driven account actions harmless.

## Local/staging setup (not applied to production)

### Bounded revocation retries (Step 11)

The BFF starts its own retry worker on startup and stops it on shutdown. It scans the dedicated `nestora:revocation:*` Redis namespace every five seconds, uses non-blocking fenced claims across instances, and processes at most four jobs concurrently. No extra process, cron, dependency, environment variable, Supabase setting or SQL migration is required. Deploy/restart the updated BFF normally; keep the existing Redis endpoint and encryption key consistent across instances. Redis ACLs must permit `SCAN` in addition to the existing GET/SET/DEL/EVAL commands. Production still requires the existing private TLS Redis deployment and suitable persistence/HA; a Redis outage fails closed and cannot guarantee durable revocation capture.

Jobs contain only the encrypted access token needed for `POST /auth/v1/logout?scope=local`. Refresh tokens are not queued, refreshed, or used to create new sessions. Storage is capped at 15 minutes or the access-token expiry, whichever comes first, with at most five attempts including the immediate attempt. Network/timeout failures, HTTP 408/429 and 5xx responses use exponential backoff with jitter and respect Retry-After. Terminal outcomes discard credentials and retain only a bounded encrypted status receipt. Restarting a BFF resumes due jobs from Redis without resetting their attempt count or deadline.

Only a successful upstream HTTP response produces `confirmed`. Recognized structured credential errors produce `already_invalid`, which does not claim that a refresh token was revoked. Other non-retryable failures remain `uncertain`; bare 401/403/404 statuses are never proof of revocation. Logout retains its existing `localSessionCleared` and `remoteRevocationConfirmed` fields and adds token-free `revocationStatus` and `revocationRetryScheduled` fields. No frontend change is required.

Extended outages, exhausted attempts, missing receipts, or expired access credentials can leave remote revocation unconfirmed. The worker deliberately does not retain refresh tokens or refresh credentials merely to extend this window. Such failures never re-enable a locally deleted BFF session. Supabase access JWTs may remain valid until their own expiry even after successful local-scope logout; logout does not terminate other devices' sessions.

1. Install the isolated backend dependencies with `npm ci` **from the bff directory**. Backend dependencies and lockfile are separate from Angular.
2. Copy `bff/.env.example` to `bff/.env`. Set the existing Supabase URL and publishable/anon key, Redis URL, a new random 32-byte base64 session encryption key and the exact browser origin. For a separate staging Supabase project, also match the public URL/key in `src/environments/environment.bff.ts`, so generated public media URLs point at that project. Never put Redis credentials or the session encryption key under src, and never configure a service-role/secret key. Keep the encryption key stable across replicas and restarts; replacing it invalidates existing encrypted records and requires coordinated relogin.
3. Use a disposable Redis service for development/staging. Set `BFF_ENABLED=true` only there. `npm run bff:dev` loads the server-only `.env`; `npm start` or `npm run start:bff` starts Angular at `http://localhost:4300`, with `/api` proxying to loopback port 3000. Set the local `BFF_ORIGIN=http://localhost:4300`. Cookie flags stay Secure/HttpOnly; browsers provide a localhost exception for Secure cookies. All non-local deployments still require HTTPS. See LOCAL_STARTUP.md for the current Windows commands.
4. Manually configure the Supabase Auth redirect allowlist for the exact staging/production origin and `/api/customer/auth/callback` (including the flow query). Check email templates use Supabase's confirmation URL/PKCE flow rather than old implicit JWT fragments. Google still redirects to Supabase's normal provider callback; Supabase then redirects the authorization code to the BFF. Do not put the Angular `/auth/customer-callback` URL in place of the BFF OAuth redirect. No Auth settings were changed automatically.
5. Run a persistent Node 22+ service behind the same-origin ingress. `bff/nginx.example.conf` shows static Angular hosting plus `/api`, including unbuffered SSE. Node binds loopback; containers need an ingress/sidecar sharing that network namespace or an explicitly reviewed binding/network change. Do not deploy this as a stateless function that loses long-lived SSE connections. Trust only your ingress for forwarded client IPs; the current server trusts loopback proxies only.
6. Build staging Angular with `npm run build:bff-client`. Its output is isolated in `dist/nestora-bff-staging`; the ordinary production build keeps `bffEnabled=false`. Build Node with `npm run bff:build`, then start it from the bff directory using `npm start`. The Dockerfile is an optional packaging example; no image was deployed.

Both flags are independent and explicit. The BFF client never falls back to direct Supabase authentication when `/api` is disabled or unavailable. Disabling the backend while leaving that client selected fails closed. Reverting to legacy authentication reintroduces browser tokens and requires an explicit security decision.

## Required migration behavior

Existing legacy browser sessions are not imported into the BFF. On first BFF client creation the two legacy auth/user/PKCE storage keys are cleared, preserving carts, recently viewed data, language and remember-me preferences. Users sign in again to obtain independent opaque cookies. The non-secret logout-pending marker blocks reuse of an offline session until backend logout can be completed; a failed network logout cannot promise remote invalidation.

Coordinate service-worker/client refresh during rollout. A previously cached legacy application can continue using its old login flow until upgraded. Validate fresh and existing tabs, update readiness and a controlled reload before claiming the site-wide token-free migration is complete. Do not clear all browser storage or guest carts as a shortcut. Old implicit auth/recovery email links should be replaced with the reviewed code flow; no client-side token handoff or encoded-token migration is implemented.

No Supabase SQL, tables, functions, RLS, Storage policies or authentication settings were changed. Pending Phase 2 SQL was not run. The BFF enforces its own active-audience/profile-field checks, but it does not repair existing direct Supabase API policy gaps for external callers. Preserve the separate Phase 2 manual approval process.

## Validation and activation gate

Automated backend tests use the real Supabase SDK with controlled upstream HTTP and WebSocket fixtures, plus a test-only store. They exercise Admin/Customer login, isolation, safe cookies/response bodies, role/deactivation checks, CSRF, refresh races, expiry, logout, PKCE callback/replay, cross-browser email flows, recovery-only permissions, checkout argument/idempotency forwarding, avatars, egress rejection and actual upstream-WebSocket-to-SSE delivery followed by logout. Route coverage tests inventory all literal application table/RPC calls. Angular tests verify token-free interfaces, `/api` routing, no auth storage, CSRF, uploads, recovery events and no direct-auth fallback, alongside the existing suite.

The real Redis integration test runs only when `BFF_TEST_REDIS_URL` points at a disposable database. It checks concurrent leases, fenced writes, atomic one-time consumption and expiry. This environment has no Redis/Docker/WSL service, so that test is explicitly skipped. No production account, real order or production database was mutated by tests.

Before activation, validate all of the following on a connected staging stack:

- Real Redis failover/outages, concurrent refresh across at least two Node instances, encryption key consistency, cookie rotation/expiry and logout while requests/streams are active.
- Real active Customer, Admin and Super Admin accounts; simultaneous audiences, remember-me, browser reload, multiple Chrome/Edge tabs, service-worker upgrade and offline logout retry.
- Google provider redirects, declined consent, expired/replayed codes, signup email confirmation and password recovery in the original and a different browser. Verify actual templates/redirect allowlists do not produce access/refresh tokens or old JWT fragments.
- DevTools Network, browser storage and WebSocket/SSE frames: no Supabase access/refresh/provider tokens; cookies contain only opaque values and have Secure/HttpOnly/SameSite attributes. Login/session responses contain only sanitized fields. Test the running Angular application, not only raw endpoints.
- Guest and signed-in checkout, cart/history merge, wishlist, discounts/free gifts, loyalty/redemptions, saved addresses, password change, orders, uploads/media, private Realtime, dashboard charts and Export Report with real staging data. Check side effects and idempotency after errors, not just HTTP status.
- Validate deployed RLS behavior, relation projections, resource/bucket allowlists and business RPC return shapes. Unknown/new routes intentionally fail closed until reviewed. Use the existing Phase 2 staging acceptance checklist where relevant without executing its SQL automatically.

Live Supabase credentials, Google provider configuration, a real shared Redis endpoint, the final hosting origin/ingress and browser acceptance evidence are not available in this workspace. These checks remain incomplete; production activation stays disabled. Automated fixtures establish transport/security behavior, not a claim that real Google login or real checkout already passed.
